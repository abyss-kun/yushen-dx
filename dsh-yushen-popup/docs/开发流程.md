# 开发流程（这个插件照着走）

> 一页纸，给任何要改这个插件的人（包括我）看。
> 起因：2026-11-12 老板问「正常一个程序员做项目是什么流程」，对照下来发现这个项目漏了第 2 步（状态表）和第 5 步（改前先跑测试），所以出现了"修一处、坏一处"。

## 0. 一条命令先跑一遍

```powershell
node --experimental-vm-modules scripts/check-all.mjs
```

它同时跑：

- `scripts/selftest.mjs` —— 零件级自检（40 项：按钮、收起、缩放、设置、路径、默认值…）
- `scripts/usertest.mjs` —— 用户视角实测（10 项：真去点、真按 Esc、真滚轮、真改设置）

**两条都必须绿。红着不许改代码。**

## 1. 先写清要什么、不要什么

- 要什么：一句话（给谁、解决什么）；
- 不要什么：边界（不联网 / 不替人做决定 / 不动别的插件的数据）；
- 验收：什么样算做完。

## 2. 先看状态表，再动手

打开 [弹窗状态.md](弹窗状态.md)：五个状态、允许怎么进出、每条不变量。

**改行为之前，先确认它落在哪个状态**。落不进去说明设计没想清楚，先补表。

## 3. 一次只改一件事

拆成能单独验证的小步：画出来 → 点得动 → 状态对 → 能回去。
一步一验证，不要攒到最后一起测。

## 4. 三层测试

| 层 | 用什么 | 谁来做 |
|---|---|---|
| 零件 | `selftest.mjs` | 机器 |
| 交互 | `usertest.mjs` | 机器（模拟点击/滚轮/Esc） |
| 观感 | 截图给你看 | 人 |

前两层必须全绿；第三层**每次涉及视觉改动都要请老板看一眼**，看完再算完。

## 5. 改的顺序（这条最容易省，也最容易出事）

1. 先跑 `check-all`，确认是绿的；
2. 改；
3. 再跑 `check-all`；
4. 红了 → 修到绿；不许"先这样吧"。

两条都绿＝可以交；只跑了一次＝没测。

## 6. 修 bug 必须补一条测试

修完就加一条能复现它的断言（至少能证明"这个坑不会再踩"）。
没有断言＝下次一定改回去。

## 7. 提交与发布

- 提交信息写**为什么**，不只写改了什么；
- 改行为就升版本号（`package.json` 的 version）；
- 重打发布包：`D:\deepseekTools\dsh-yushen-popup-发布\`；
- 推到 GitHub：`abyss-kun/yushen-dx` 的 `dsh-yushen-popup/`。

## 8. 上线后看日志

`~/.dsh/dsh-yushen-popup/diag.jsonl`（老的还可能在 `~/.dsh/dayu/runtime/popup-diag.jsonl`）。

它记：点了什么按钮、按没按 Esc、有没有因为读不到用量报警。
界面上"点了没反应"这类问题，先看这里——**有没有记录**能直接区分"事件没到"和"到了没生效"。

## 交付前的清单

- [ ] `check-all` 两条全绿
- [ ] 涉及视觉的，请老板看过并说 OK
- [ ] 修过的 bug 都补了断言
- [ ] 版本号改了、发布包重打了
- [ ] GitHub 推了
- [ ] 交接里写一句"这轮改了什么、还剩什么"

## 为什么定这么死

弹窗是"一个有五种状态的界面元素"，不是一段独立的函数：按钮、收起、位置、开关互相咬。
少一条断言，就会出现"关闭后还显示数字""两幅叠着""开关关不掉"这种看着很蠢、但每次都要用户重新报一遍的问题。
断言跑一遍只要几秒，让你重报一遍要花半天。
