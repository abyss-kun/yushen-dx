## 二、逐条

### ① 启动死循环：`Web authentication failed`

| | |
| --- | --- |
| 现象 | 启动必弹错误框，点重启无限循环，连登录界面都到不了 |
| 根因 | 之前的崩溃把 `.credentials.yaml` 凭据和壳的会话 Cookie 状态写坏 → 拿无效通行证验证本地服务 → 401 → 崩 → 状态更坏 |
| 与版本无关 | rc.2 / rc.3 在同样的坏状态下都崩 |

**修法（dsh-guard 做的就是这四步，顺序不能换）**

1. 关掉所有 DSH 进程
2. 备份并删除壳的会话目录：`%APPDATA%\@deepseek-ai\dsh-desktop\Network`、`Session Storage`
3. 删掉残留的 `lockfile`
4. 把 `~/.dsh/.credentials.yaml` 改名（`.bak-<时间戳>`），强制全新登录

**残留影响（这条最容易漏）**：重置之后的旧会话里，附件引用已经悬空；旧会话只能只读、不能续跑，一续跑必炸。判断方法见第五节 `session-doctor`。

**怎么判断已经根治**：最新一条崩溃日志的时间**早于当前进程启动时间** → 那次之后没再崩过。工具里这个状态叫 `authCrash: stale`，不要拿三天前的旧日志冒充"现在还在崩"。

### ② 渲染进程反复崩溃：`Desktop renderer exited: crashed`

| | |
| --- | --- |
| 现象 | 用着用着界面崩掉，弹"应用无法启动或已意外停止"，没有报错细节 |
| 根因 | **OrayIddDriver**（向日葵远程的虚拟显示器，2022 年老驱动）——Electron 渲染进程枚举/使用它时随机崩 |
| 修法 | 管理员执行 `pnputil /disable-device "ROOT\DISPLAY\0000"`，立即根治 |
| 副作用 | 向日葵的虚拟屏幕功能暂时不可用；要恢复用 `/enable-device` |
| 辅助 | 清过一轮 GPU/着色器缓存，原样备份在 `D:\DSH\私人恢复备份\gpu-cache-bak-20261024-2208` |

**推广规则**：以后遇到"渲染类崩溃"（renderer crashed / 白屏 / GPU 相关），**先查有没有虚拟显示器驱动**（Oray、IDD、Parsec、spacedesk、usbmmidd、Sunshine/Apollo、ToDesk 等）。Electron 对它们的兼容性很差，这不需要重装 DSH。

### ③ 任务报错：`Attachment object is missing`

两层原因，缺一不可：

1. **模型配置没声明图片输入**：`cordis.patch.yml` 里没写 `input: [text, image]` —— 已在补丁里补上，重启生效。
2. **重置前的旧会话附件引用悬空**：那些 sha256 对象已经不在 `~/.dsh/attachments/v1/objects/` 里了。

**修法**：新会话 + 重新上传附件；旧会话弃用，不要试图续跑。

### ④ 附带发现：LightingService 每 2~4 分钟崩一次（0xc0000005）

华硕灯效服务，**与 DSH 无关**，但日志噪音很大。当时已把进程停掉；要永久禁用需要管理员执行：

```powershell
Set-Service -Name LightingService -StartupType Disabled
```

## 四、修复工具覆盖到哪（诚实版）

工具：`dsh-yushen-twins\assets\repair-helper\YushenRepair.exe`（本地未签名，`--diagnose` 只读）。

| 故障 | 能诊断 | 能修 |
| --- | --- | --- |
| ① 认证死循环 | 是（`authCrash` / `shellCache` / `shellLockfile`） | 是：「重置登录状态」——先全量备份，再清壳缓存、删 lockfile、改名凭据；宿主在跑会拒绝 |
| ② 渲染崩溃（虚拟显示器） | 是（`virtualDisplay: oray / virtual / none`） | **否**：禁用驱动要管理员，工具只给命令 |
| ③ 附件悬空 | 用 `scripts/session-doctor.mjs`（会话是 zstd，C# 解不了） | **否**：只能弃用旧会话，靠新会话重传 |
| ④ 灯效服务 | 是（`lightingService: disabled/demand/auto(+running)`） | **否**：同样要管理员 |
| profile JSON 坏 / STOP.flag / 僵尸 lock / 桥接依赖缺失 | 是 | profile 和两个 flag 能修；依赖只能报告 |

**为什么附件巡视不在 exe 里**：会话是 `session.v4.jsonl.zstd`，一个文件里是多帧 zstd 首尾相接；.NET Framework 没有 zstd，Node 24 自带。所以这条用 Node 脚本，不让 exe 硬扛。

## 五、怎么用（命令都在本机）

```powershell
# 只读诊断：六类分类 + 九项检查 + 固定建议
.\assets\repair-helper\YushenRepair.exe --diagnose

# 会话与附件体检（只读）：未收尾会话、挂起的工具调用、悬空附件
node scripts\session-doctor.mjs
node scripts\session-doctor.mjs --json --strict

# 认证死循环的兜底（默认只诊断，-Repair 才动手）
powershell -ExecutionPolicy Bypass -File D:\DSH\tools\dsh-guard\dsh-guard.ps1
```

修复动作全部要求：**宿主完全退出 + 用户当场确认**；每个动作都写审计到 `~/.dsh/dayu/repair/actions.jsonl`，原始文件留 `~/.dsh/dayu/repair/backups/<时间戳>/`。

## 六、修不了怎么办：缺口闭环

修不了的项目不会消失，会走这条链：

```
修复助手诊断
   │  能修 → 用户按「修复」→ 执行 → 写审计
   │  修不了 → 写明"为什么修不了"→ 记进 gaps.jsonl（status=open）
   ▼
主人用别的办法把机器修好（管理员禁驱动、装依赖、改服务…）
   ▼
DSH 起来之后，插件启动时跑 repair-loop：
   ├─ 让助手重新只读诊断
   ├─ 台账里还 open、但证据已消失的 → 追加 resolved（标明是复核后关掉的）
   └─ 仍然修不了的 → 写一条能力请求（下一版照这个补）
```

| 文件 | 内容 |
| --- | --- |
| `~/.dsh/dayu/repair/gaps.jsonl` | 缺口台账：open / resolved，只追加，含原因与证据 |
| `~/.dsh/dayu/repair/capability-requests.jsonl` | 能力请求：某类缺口要能自修还缺什么（按 id 每天去重） |
| `repair-helper/test-gaps.ps1` | 闭环证据：先记 open，机器修好后下一次跑出 resolved |

手动验证：`node scripts\repair-loop.mjs`（只读诊断 + 台账对账，不改业务文件）。
插件启动时自动跑这一圈，失败静默、一次进程只跑一次（见 `index.js` 末尾的 repair-loop 挂载）。

## 七、给后续接手的人

1. **判断"现在还在崩吗"，看日志时间与进程启动时间的先后**，不要看到旧日志就重置。
2. **崩溃重置之后，旧会话只读、不续跑**；先跑 `session-doctor`，别直接点"继续"。
3. **渲染崩溃先怀疑虚拟显示器**，别先怀疑鱼神或 DSH 版本。
4. 任何修复前先备份；修复完留下证据（审计行、备份目录、诊断 JSON）。
5. 这里写的都是已验证过的事实；有新故障就往下追加一节，别改历史结论。
